This handbook explains how to operate Tiny Swarm World from a Linux or WSL
shell without reading source code or raw local credential files as the normal
navigation method. It references local ignored files only where an operator
must intentionally provide an override.

== Operating Model

Tiny Swarm World prepares a local Docker Swarm target environment on managed
LXC nodes through Incus. The supported operator surface is the
`tiny-swarm-world` CLI and the Linux/WSL `install.sh` wrapper. Multipass and
Windows-native execution are not supported node-provider paths.

== Intended Identity Boundary

Tiny Swarm World is an internal development and test environment tool. The
deterministic catalog values are `INTERNAL/TEST ONLY` material for disposable
local acceptance; unchanged defaults are not suitable for production, shared,
public, or untrusted exposure.

Enterprise identity and reachability remain outside the bootstrap path. AD,
LDAP, SSO, VPN, firewall, network segmentation, and IAM policy are supplied
and governed by the surrounding organization. When stronger or environment-
specific credentials are required, provide them through the documented
protected operator override or applicable Infisical path; do not edit the
catalog or copy passwords into evidence.

== Before You Start

Use a Linux or WSL2 shell from the repository root. Prepare:

* Python 3.12 or newer, with virtual-environment support;
* Git;
* Incus/LXD host management initialized before the project run; the supported
  default backend is Incus;
* `incus`/`lxc` usable without `sudo` from the same Linux/WSL shell that runs
  `./install.sh`;
* `socat` when WSL localhost forwarding is required.
* Optional Docker CLI access for host-side diagnostics and cache helpers; host
  Docker is not the managed Swarm workload runtime.

Incus/LXD installation, initialization, storage, networks, profiles, daemon
repair, and group membership are host responsibilities. Tiny Swarm World does
not install or initialize the provider automatically. After changing host
group membership, reopen the Linux/WSL shell and verify `incus version` and
`incus info` without `sudo`. Use the canonical prerequisite and smoke checklist
in `documentation/user_guide/installation.adoc` before starting a live run.

The ready-for-install checklist is the single operator entry point for the
preflight, optional temporary-container smoke, and handoff to the ordered
installation path. Do not use this handbook as a second command catalogue.

=== Complete The Required Windows Prework For WSL2

When running Tiny Swarm World in WSL2 with the default Windows exposure, prepare
the Windows side *before* starting `./install.sh`. The installer deliberately
stops before platform mutation when this bridge is missing, degraded, or stale.

First confirm from Windows PowerShell that the intended WSL2 distribution is
running and uses `systemd` as PID 1:

[source,powershell]
----
wsl --list --verbose
wsl -d <DistributionName> --exec sh -lc "ps -p 1 -o comm="
----

The second command must print `systemd`. Then open *PowerShell as
Administrator* in the Tiny Swarm World repository root. If this is not the
Windows default WSL distribution, first set its exact name in
`tools/windows/tws-wsl-bridge.config.json` instead of keeping the automatic
`"distro": "auto"` selection. Then run:

[source,powershell]
----
Set-ExecutionPolicy -Scope Process Bypass
.\tools\windows\tws-wsl-bridge.ps1 -Action prerequisites
.\tools\windows\tws-wsl-bridge.ps1 -Action install
----

The first service installation opens a Windows credential dialog. Use the
Windows account that owns the WSL distribution and enter its normal Windows
password, not the Windows Hello PIN. The password is passed to the Windows
Service Control Manager and is not stored in the repository.

Installation publishes a protected runtime bundle below
`%ProgramData%\TinySwarmWorld\WslBridge`; the service does not execute mutable
files directly from the checkout. Re-run the elevated `-Action install` after
reviewed bridge, configuration, or port-registry changes to upgrade that
bundle.

The protected heartbeat is stored at
`%ProgramData%\TinySwarmWorld\WslBridge\bridge-state.json` and read from WSL via
`/mnt/c/ProgramData/TinySwarmWorld/WslBridge/bridge-state.json`. The service does
not write a checkout mirror. Hosts with a non-default WSL automount must expose
the canonical ProgramData location before live setup.

The tracked default uses `"listenAddress": "0.0.0.0"` and managed inbound
Firewall rules, so its listeners are not limited to Windows loopback. Review
the bridge configuration and Windows network profile before installation when
the host is connected to an untrusted network.

Verify the completed prework before returning to the WSL shell:

[source,powershell]
----
Get-Service -Name TinySwarmWorldWslBridge
.\tools\windows\tws-wsl-bridge.ps1 -Action status
----

The service must report `Running`, and bridge discovery must report `READY`.
The service then keeps the Windows portproxy, Firewall, `*.tsw.local` hosts
entries, and current WSL address aligned automatically.

Only when Windows browser and localhost exposure are intentionally not needed,
disable that contract explicitly in the WSL shell before installation:

[source,bash]
----
export TSW_WINDOWS_EXPOSURE=disabled
----

See `tools/windows/README.windows-wsl-bridge.md` for distro selection, repair,
status, verification, and uninstall details.

Install the Python package in editable mode:

[source,bash]
----
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install --require-hashes -r requirements.lock
python3 -m pip install --no-deps -e .
----

Check the installed CLI and static preflight without live infrastructure
mutation:

[source,bash]
----
tiny-swarm-world --list-workflows
tiny-swarm-world --preflight
----

Contributors can additionally install `requirements-dev.txt` and run
`python3 tools/quality_gate.py quality`. Those tools are not installed by
the runtime-only instructions above.

If the package is not installed yet but its runtime dependencies are available,
use the source checkout fallback:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world --list-workflows
PYTHONPATH=src python3 -m tiny_swarm_world --preflight
----

== Prepare Operator Configuration

For a standard internal-test installation, no credential file is required.
The installer uses the
link:arc42/08_configuration/internal-test-credential-catalog.md[central catalog],
including its service-specific exceptions.

For intentional overrides, use
link:user_guide/installation.adoc#operator-credential-overrides[the canonical optional override procedure].
A file-based override must be a user-owned `0600` regular file inside a
user-owned `0700` directory on a Linux-native filesystem. Select it explicitly
with `TSW_INSTALL_ENV_FILE`; keep that selection when starting a new shell.
Do not copy or print credentials into logs or tickets.

The current workflow starts self-hosted Infisical from catalog/operator inputs.
Service-item synchronization is a separate step after readiness; external
Infisical mode is not supported by this workflow. See
link:arc42/08_configuration/credential-source-precedence.md[source precedence].

== Run The Guided Installation

*This command resets the managed environment before installing it.*
Preserve needed data and complete the
link:user_guide/installation.adoc#ready-for-install-checklist[ready-for-install checklist]
first. Then, for an intentional fresh installation with evidence capture:

[source,bash]
----
./install.sh
----

The wrapper first asks for the reset phrase `RESET_TINY_SWARM_PLATFORM`, then
runs the governed platform reset, then starts `setup run --live` with the
default `service-access` profile. The CLI live prompt is separate:

[source,text]
----
Live setup can change local infrastructure. Continue? [y/N]:
----

Answer `y` only when changing local Incus/LXC state, Docker Swarm,
networking, Portainer, Nexus, service stacks, images, and credentials is
intentional.

These are alternative fresh-reset invocations, not consecutive steps. Use
them only for deliberate test-system recreation:

[source,bash]
----
./install.sh --confirm-reset
./install.sh --confirm-reset --non-interactive-live-approval
----

For headless systems:

[source,bash]
----
./install.sh --headless
TSW_INSTALL_HEADLESS=1 ./install.sh
----

Use the evidence directory printed by the installer. In this main revision,
the wrapper writes run context, reset logs, setup logs and exit codes below:

[source,text]
----
${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/evidence/installation-tests/<host-runtime>/<UTC timestamp>/
----

`<host-runtime>` is `wsl2` for WSL2 and `native_linux` for native Linux.
`TSW_LIVE_EVIDENCE_ROOT`, when set, replaces the root before the host/runtime
subdirectories are appended. These directories use protected Linux-native
storage. Checkout-local installation evidence from older runs is historical.

== Use The CLI Directly

List supported workflows:

[source,bash]
----
tiny-swarm-world --list-workflows
----

Run a non-mutating preflight:

[source,bash]
----
tiny-swarm-world --preflight
tiny-swarm-world --lxc-backend incus --preflight
----

The direct setup command does not perform the wrapper's preliminary reset.
It still mutates infrastructure and requires the same effective service
configuration. Read link:user_guide/usage.adoc#daily-operation[Daily operation]
before switching entry points:

[source,bash]
----
tiny-swarm-world setup run --live
tiny-swarm-world --lxc-backend incus setup run --live
----

Run read-only post-install verification:

[source,bash]
----
tiny-swarm-world platform verify
----

Reset or destroy require exact confirmation and live consent:

[source,bash]
----
tiny-swarm-world platform reset --confirm RESET_TINY_SWARM_PLATFORM --live
tiny-swarm-world platform destroy --confirm DESTROY_TINY_SWARM_PLATFORM --live
----

== Open The Services

The default full setup uses the `service-access` profile. After a verified
deployment, use the Service Access landing page as the operator start page:

[source,text]
----
https://service-access.tsw.local
----

The dashboard is generated from the selected configuration. Its links are
access targets, not proof of deployed, healthy or authenticated services.
Open the page from the browser you intend to use; that browser's host must
resolve the names, reach the forwarded ports and trust the configured TLS CA.

Common preferred local service routes are:

[options="header"]
|===
| Service | Preferred route | Notes
| Service Access | `https://service-access.tsw.local` | Generated management table with service links and Infisical item references.
| Infisical | `https://infisical.tsw.local` | Secret-management UI for authorized operators.
| Portainer | `https://portainer.tsw.local` | Deployment gateway after bootstrap.
| Nexus | `https://nexus.tsw.local` | Repository service and Docker proxy behavior.
| Jenkins | `https://jenkins.tsw.local` | CI service.
| Pulsar | `https://pulsar.tsw.local` | Pulsar Manager UI; use the catalog or effective override. The Infisical item is usable only after synchronization.
| Pulsar Admin API | `https://pulsar-api.tsw.local/admin/v2/clusters` | Requires the effective bearer token; browser reachability is not an authenticated API check.
| SonarQube | `https://sonarqube.tsw.local` | Static analysis service.
| Swagger/NGINX | `https://swagger.tsw.local` | API documentation surface.
| Traefik | ports `80` and `443` | Ingress owner for the service-access setup profile.
|===

Direct localhost ports such as `10000`, `10001`, `11080`, `12000`, `13081`,
`14080`, `14081`, `16081`, and `17080` are diagnostic or compatibility access.
They are not the preferred Service Access links. Localhost reachability depends
on the selected provider, LXC profile proxy state, WSL forwarding, and verified
stack deployment. Treat route defaults as operator targets, not proof that a
service is healthy.

== Get Infisical Credentials

Infisical has two distinct credential concerns:

* bootstrap login credentials for the Infisical UI;
* service credential entries synchronized into or referenced from Infisical.

The bootstrap login email and initial admin password are resolved during
installation from the deterministic catalog unless explicitly overridden in
the process environment or protected local source. The canonical internal-test
login identifier is `admin@tiny-swarm-world.local`; the catalog documents the
disposable password convention. The installer prints the URL and identifier,
but intentionally does not print password values.

For an explicit override, use the protected file selected by
`TSW_INSTALL_ENV_FILE` or the applicable configured source. A default install
does not create a file for you. Do not assume a key's presence alone proves
that its value is valid or in use.

For the standard internal-test path, use the catalog's documented disposable
login convention. For an explicit override, open the ignored local file in a
private terminal or editor to read the bootstrap email and password, then use
those values to sign in to Infisical at the configured Infisical route. The
default external URL is:

[source,text]
----
https://infisical.tsw.local
----

The direct `http://localhost:17080` URL remains a diagnostic compatibility
target when provider forwarding exposes it.

The installer uses the resolved catalog values and optional operator overrides
for Infisical bootstrap. It does not write a separate Infisical credential or
recovery file.

After signing in, use the Infisical UI to reveal or copy service secret values.
The Service Access dashboard intentionally shows only users and Infisical item
references; it does not display password values. If Infisical item
synchronization has not been enabled or completed, use the catalog for defaults
or your protected source for overrides. No generated local credential file is
implied; dashboard references are only navigation hints.

Optional legacy Infisical item seeding can be requested before a deliberate
fresh installation. *The following command resets the managed environment; do
not use it just to populate missing items in an existing installation.* For
that case, review the supported synchronization contract first.

For a deliberately disposable fresh run:

[source,bash]
----
export TSW_SEED_INFISICAL_ITEMS=1
./install.sh --confirm-reset
----

The default installer value is `TSW_SEED_INFISICAL_ITEMS=0`, so do not assume
that every catalog-managed service credential has already been copied into
Infisical unless the setup evidence confirms it.

== Verify A Finished Installation

Use the non-mutating workflow first:

[source,bash]
----
tiny-swarm-world platform verify
----

Use the directory printed by that run. On this main revision, you can locate
candidate evidence files under the default path:

[source,bash]
----
TSW_INSTALL_EVIDENCE_ROOT="${TSW_LIVE_EVIDENCE_ROOT:-${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/evidence/installation-tests}"
find "$TSW_INSTALL_EVIDENCE_ROOT" -maxdepth 3 -type f \
  \( -name 'context.txt' -o -name 'reset-run.exit' -o -name 'setup-run.exit' \) \
  -print
----

Useful provider checks, using the backend selected for the run:

[source,bash]
----
incus list
incus exec swarm-manager -- docker node ls
incus exec swarm-manager -- docker stack ls
incus exec swarm-manager -- docker service ls
----

== Troubleshooting Checklist

Use the concise decision path in
link:user_guide/troubleshooting.adoc#first-response[Troubleshooting]
to classify the first failed phase. That page is the canonical source for
bounded Incus profile/reset actions, APT/network recovery, WSL bridge repair,
port ownership, service reachability, and the install debugger.

Inspect the newest evidence and correct the named prerequisite. Choose the
least disruptive supported retry through
link:user_guide/usage.adoc#daily-operation[Daily operation]; rerunning the fresh
installer includes another reset. Do not use broad Incus cleanup, copy secrets or
join tokens into reports, or treat a static configuration check as live service
success.

== Update Status

This revision has no supported `./install.sh --update` command. The canonical
update workflow and its verification on both host types are tracked in
https://github.com/MatthiasBurger-Coder/Tiny-Swarm-World/issues/297[#297].
Neither a fresh reset nor platform reconciliation establishes a product upgrade.
