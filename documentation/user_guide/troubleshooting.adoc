= Troubleshooting

[[first-response]]
== First Response For Operators

Start in the repository root with the same Python environment, service profile
and configuration used by the failing run. Preserve its evidence directory.

. Read the first failed phase and the printed evidence path.
. Inspect `reset-run.exit` and, if it exists, `setup-run.exit` in that directory.
  If reset failed, setup was not started and its exit file may be absent.
. Run static diagnostics after runtime dependencies are available:
+
[source,bash]
----
source .venv/bin/activate
python3 tools/install_debugger.py
tiny-swarm-world --preflight
----
. For an installed environment, use `platform verify` before selecting a
  repair. It does not modify the platform.
. Correct the named cause and choose the operation in
  link:usage.adoc#daily-operation[Daily operation]. Do not automatically rerun
  `./install.sh`: it resets managed state.

[options="header"]
|===
| What you see | Next check
| `ModuleNotFoundError` or missing CLI | Activate `.venv` and complete link:installation.adoc#_python_environment[Python Environment]; do not reset the platform.
| Override permission error | Verify file ownership, `0600` file and `0700` parent on a Linux-native filesystem; see link:installation.adoc#operator-credential-overrides[optional overrides].
| No password file after installation | Normal for the default path. Use the link:../arc42/08_configuration/internal-test-credential-catalog.md[credential catalog].
| Login page responds but login fails | Check the effective service identity and credential source; HTTP 200 is not authentication.
| DNS, connection or certificate error | Diagnose name resolution, forwarding and TLS separately from credentials.
| Missing `--update` option | This revision has no supported update command; see https://github.com/MatthiasBurger-Coder/Tiny-Swarm-World/issues/297[#297].
|===

Before reporting a problem, record the commit (`git rev-parse HEAD`), host
type, selected profile, failed phase, exit code and redacted error summary.
Inspect logs privately and remove credentials, tokens, cookies, private keys
and sensitive command output before sharing. A printed log path is not a
redaction guarantee.

The detailed sections below cover individual failures. Development quality
tools are needed only when running the corresponding developer checks.

== Quality Gate Fails: Missing Tool

If Ruff, mypy, import-linter, or the Requests type stubs are missing, install
the development tools in the active Python environment:

[source,bash]
----
python3 -m pip install -r requirements-dev.txt
----

Then rerun:

[source,bash]
----
python3 tools/quality_gate.py quality
----

== Import Errors For tiny_swarm_world

Activate the environment and install the runtime package from the repository
root as described in link:installation.adoc#_python_environment[Python Environment].
Verify imports without starting infrastructure:

[source,bash]
----
python3 -c 'import tiny_swarm_world; import pydantic; import yaml; import requests'
----

Source-checkout commands additionally need `PYTHONPATH=src`. The quality gate
sets that variable itself, but it does not install missing dependencies.

== import-linter Cannot Find Configuration

The architecture lint gate expects `.importlinter` in the repository root.
Run the gate from the repository root, not from a source or test subdirectory.

== Common Failure Decision Path

Start with the newest evidence directory and the first failed phase. Do not
repeat a mutating command until the named prerequisite is corrected and live
consent is still intentional. Use the detailed section named in the table for
the bounded commands and evidence interpretation.

[options="header"]
|===
| Symptom or marker | First bounded action | Detailed source

| `REFUSED_LIVE_CONSENT_MISSING`
| Add `--live` only when local mutation is intentional; otherwise keep the run static.
| `REFUSED_LIVE_CONSENT_MISSING` below

| Incus/LXD command unavailable, daemon denied, or profile/storage not ready
| From the installer shell, run `incus version` and `incus info` without `sudo`, then run static preflight.
| LXC Native Provider Is Not Ready below

| `managed_nodes_reset_blocked` or `unsafe_instance_config`
| Inspect the named node/profile markers and guarded settings; never use broad container cleanup.
| `REFUSED_WORKFLOW_CONFIRMATION_MISSING` below

| `platform init: failed_to_apply` with `apt_repository_unreachable`
| Run read-only network diagnosis, then configure only LXC-reachable APT mirrors if needed.
| Docker Installation Fails During Platform Init below

| Occupied ports or `WINDOWS-WSL-BRIDGE`
| Inspect expected ownership and bridge status; repair only service-owned state with explicit approval.
| WSL2 Setup Stops At WINDOWS-WSL-BRIDGE below

| Service endpoint unavailable after setup
| Verify profile, managed-node services, routing ports, and current WSL forwarding; do not infer live success from static configuration.
| Service Access Is Not Reachable below
|===

The default quality gate and static preflight do not perform these live recovery
actions. Never paste secrets, join tokens, or host-specific IPs into shared
evidence.

== LXC Native Provider Is Not Ready

The default node provider is `lxc_native` through Incus. Check the
selected backend from the same Linux/WSL shell that will run Tiny Swarm World.
Incus/LXD is a host prerequisite: Tiny Swarm World does not install or
initialize it, repair its daemon, create its storage/network/profile state, or
change host group membership. The current user must run the provider client
without `sudo` from that same shell. Use the canonical prerequisite checklist
in `documentation/user_guide/installation.adoc` before applying a recovery
action. If the optional temporary-container smoke is needed, follow the
bounded sequence in that checklist and delete only its named test container.

For Incus:

[source,bash]
----
incus version
incus info
----

If the configured backend should be selected explicitly for this run:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world --lxc-backend incus --preflight
----

In WSL, verify that the distribution is WSL2 and that systemd, cgroup, and
user namespace support are available. WSL1 is not a supported target for the
default provider.

Provider readiness checks are read-only. They do not install packages, start
or repair daemons, create profiles, change group membership, or mutate
provider networking.

== Unsupported Node Provider Selection

The supported node provider is `lxc_native`. If an old command line uses a

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live
PYTHONPATH=src python3 -m tiny_swarm_world --lxc-backend incus setup run --live
----

== Artifact Contract Preflight Fails

The artifact contract preflight runs before host, platform, image or stack
mutation during `setup run`. It can fail when the selected service profile has
an image without a matching contract, a contract has an implicit `latest` or
mutable reference, image targets or build contexts conflict, or a repository-
local build context is missing. Resolve the reported contract target or
context and rerun the non-mutating checks before attempting live setup. A
static failure means that `docker build`, pull, push and dependent deployment
were not authorized by the artifact phase.

The default profile is `service-access`; pass `--service-profile default` only
when the base profile is intentionally selected. Image overrides are resolved
once for Compose rendering and artifact preparation. Review supported
`TSW_*_IMAGE` values in the configuration contract before changing an image
reference, and keep tags or digests immutable.

== Artifact Readiness Gate Blocks Setup

After the required Nexus and registry bootstrap, the setup workflow checks the
manager Docker daemon, registry endpoint, Nexus endpoint and repositories,
manager storage, repository build inputs, and public pull access. The checks
are bounded and read-only. A failed, unavailable, timed-out, unknown, partial
or degraded target is a mandatory blocker; `artifacts prepare`,
`artifacts verify`, and dependent deployment phases are skipped.

Readiness results contain target IDs, typed status, safe remediation and a
verification scope. They do not contain credentials, tokens, HTTP bodies,
raw command output or secret values. The canonical live policy distinguishes
`LIVE_CONSENT_MISSING`, `LIVE_PREREQUISITE_MISSING`,
`LIVE_BLOCKED_BEFORE_MUTATION`, `LIVE_PARTIAL`, `LIVE_DEGRADED`, and
`LIVE_FAILED_AFTER_MUTATION` from `LIVE_VERIFIED`. Do not treat a local quality
pass, an endpoint configuration, or a skipped live check as live success.

== Portainer Admin Initialization Returns HTTP 409

`PortainerAdminInitializationRejected HTTP 409` means Portainer rejected the
administrator initialization call. In the fresh-install path, `install.sh`
first runs the managed platform reset, so a 409 after that reset is evidence
to review rather than a readiness delay.

The deployment workflow treats a rejected initialization as already achieved
only when the same configured Portainer username and password authenticate
immediately afterward. If those requested credentials do not authenticate,
the failure stays explicit because the remaining cause is usually stale or
unmanaged Portainer state, an incomplete reset, or a credential mismatch.

Check the reset evidence first:

[source,bash]
----
# Replace this placeholder with the complete directory printed by your run.
TSW_RUN_DIR='/path/printed/by/the/installer'
cat "$TSW_RUN_DIR/reset-run.exit"
if [ -f "$TSW_RUN_DIR/setup-run.exit" ]; then
  cat "$TSW_RUN_DIR/setup-run.exit"
fi
----

Use the actual path printed by the wrapper; the placeholder above is not an
existing directory. Supported
host runtime directories are `wsl2` and `native_linux`; the run context file
also records `host_runtime_type` and `selected_evidence_directory`.

Then verify that the resolved `TSW_PORTAINER_USERNAME` and
`TSW_PORTAINER_ADMIN_PASSWORD` values are the intended values for this local
installation. They may come from the disposable catalog or an explicit
operator override. Do not paste password values into issue reports, logs, or
committed documentation.

== Installation Debugger For WSL2

Use the installation debugger when `install.sh` aborts and the next question is
whether the checkout, host runtime, WSL2 systemd availability, service
definitions, or evidence logs are the problem:

[source,bash]
----
python3 tools/install_debugger.py
----

The default mode analyzes the `install.sh` bootstrap contract, repository
permissions, ownership markers, WSL2/systemd indicators, systemd unit
definitions, and the newest installation evidence directory across supported
host directories. `install.sh` must delegate to
`python3 -m tiny_swarm_world.simple_installer`; the Python installer owns the reset,
setup, terminal recording, headless logging, and evidence policy. The debugger
also prints exact `grep`, `tail`, `systemctl`, and `journalctl` commands for
finding the abort point after a `Service` log line.

For live host diagnostics, including `systemctl is-system-running`, use:

[source,bash]
----
python3 tools/install_debugger.py --live
----

To allow narrow repository permission repairs, add `--fix-permissions`:

[source,bash]
----
python3 tools/install_debugger.py --live --fix-permissions
----

This repair mode is intentionally limited to the installer execute bit and the
local secret-file mode. Ownership mismatches are reported with a review command
instead of being changed automatically.

== WSL2 Setup Stops At WINDOWS-WSL-BRIDGE

When WSL2 live setup requires Windows browser access, Tiny Swarm World checks
the Windows-side bridge before platform mutation. A failed
`WINDOWS-WSL-BRIDGE` preflight check means the Windows portproxy, Firewall,
hosts-file and Windows service bridge has not been prepared, is stale, or no
longer matches the current WSL IP. A legacy bridge without a supported
discovery-agent contract is also rejected.

Prepare or repair it from elevated Windows PowerShell:

[source,powershell]
----
cd D:\Projects\Tiny-Swarm-World
Set-ExecutionPolicy -Scope Process Bypass
.\tools\windows\tws-wsl-bridge.ps1 -Action install
----

After `wsl --shutdown`, the Windows service discovery agent normally repairs the
changed address within the configured interval. Trigger immediate reconcile
with:

[source,powershell]
----
Restart-Service -Name TinySwarmWorldWslBridge
----

From WSL, the same refresh can be triggered without changing Linux network
state:

[source,bash]
----
powershell.exe -NoProfile -Command "Restart-Service -Name TinySwarmWorldWslBridge"
----

The installer does not set Windows portproxy, Firewall, hosts-file or Windows
service state by itself. It requires the registered agent to have written a
`ready` heartbeat within the last five minutes. To run WSL2 without Windows
localhost exposure, set `TSW_WINDOWS_EXPOSURE=disabled` explicitly before
setup.

== Setup Preflight Reports Occupied Ports

`setup run --live` is intentionally re-runnable. During preflight, an occupied
port is accepted only when the local host probe recognizes the expected Tiny
Swarm World service on that port.

Expected already-running services are reported with
`source=existing_expected_service` and the port check passes. Unknown port
owners still fail preflight and must be stopped or remapped before live
execution.

If a port fails although the service should already be running, verify the
service from the same WSL shell:

[source,bash]
----
curl -k -s https://portainer.tsw.local/api/status
curl -k -s https://nexus.tsw.local/service/rest/v1/status
curl -s http://localhost:13500/v2/
curl -k -s https://jenkins.tsw.local/login
curl -k -s https://pulsar-api.tsw.local/admin/v2/clusters
curl -k -s https://sonarqube.tsw.local/api/system/status
----

== SonarQube Admin Access Cannot Be Reconciled

After the SonarQube stack becomes available, deployment verifies the configured
`TSW_SONARQUBE_ADMIN_PASSWORD`. If that credential is already active, no
password change is made. Otherwise the post-stack step verifies the initial
local `admin` credential, rotates it to the configured value, and verifies the
new login without writing either value to logs or evidence.

Deployment fails closed when neither the configured nor initial credential can
be verified. In that case, inspect SonarQube readiness and use the current
ignored local secret source; do not paste password values into terminal logs,
issues, or evidence. A manually changed administrator credential must first be
reconciled with the approved local secret source before rerunning deployment.

== Infisical Remains Unavailable After An Interrupted Migration

If all normal Infisical readiness attempts are exhausted, the live deployment
adapter may attempt one constrained migration-lock recovery before checking
readiness again. It discovers the active `infisical_infisical-db` Swarm task,
requires exactly one task node and one matching container, and touches only the
known `infisical_migrations_lock` and
`infisical_migrations_startup_lock` tables when those tables exist. Any
ambiguous placement, container count, database command, or update fails closed
and preserves the original readiness failure.

This is a high-impact recovery action even though its table allowlist is
fixed. Before manual database intervention, retain or snapshot the owned
Infisical database volume and inspect redacted service/task diagnostics. The
rollback for an incorrect manual database change is restoration from that
owned volume backup; do not broaden the automated table list or run arbitrary
SQL through the recovery path.

== Service Access Is Not Reachable

The full guided setup selects the service-access profile by default. The
default `lxc_native` path uses configured artifact image-publication, stack
deployment, and Swarm service-readiness contracts, but each phase can still
block or fail when live prerequisites such as registry access, external Swarm
inputs, or observed service readiness are unavailable. Service-access
dashboard and NGINX assets are committed repository inputs and are packaged
into their respective images by the artifact workflow; live reachability still
requires explicit deployment evidence.

The committed dashboard is generated from the effective service-access model.
For LXC stack deployment, the runtime renders the dashboard again and writes
the generated HTML to
`${TSW_REMOTE_STACK_ROOT}/service-access/dashboard/index.html` before the
service-access stack is deployed. The dashboard intentionally does not claim
service reachability until observed evidence exists. Password values are not
present in the dashboard; use the listed secret item reference only through
the configured secret-management surface.

Check the non-secret prerequisites before a live run:

* the service-access setup profile exposes Traefik ingress ports `80` and
  `443`;
* the service-access NGINX compose service publishes `10000` for the dashboard
  and `8086` for the Infisical compatibility route as stack metadata;
* the service-access dashboard and NGINX images are available to the Swarm
  registry;
* the service-access dashboard stack asset preparation step has synchronized
  the generated `dashboard/index.html` under the remote stack root;
* the service-access stack has been deployed intentionally through a reviewed
  live path.

In WSL, `localhost`, `localhost:10000`, and `localhost:8086` depend on host-forwarding state
and may be out of sync even when the stack is reachable on the Swarm node IPs.
The service-access setup profile treats an unexpected local listener on those
ports as a mandatory preflight blocker. If `http://localhost:10000` returns an
unexpected page, clear the stale local listener or redeploy the updated
service-access stack.

Preferred HTTP access uses Traefik host routes such as
`https://service-access.tsw.local`; direct localhost ports are diagnostic or
compatibility surfaces.

Endpoint configuration does not prove service health. Treat local route
defaults as operator targets only; use deployment verification or explicit live
smoke evidence before claiming a service is reachable.

If deployment apply reports `failed_to_prepare`, inspect the routing-evidence
write before investigating Docker. The target is
`.tiny-swarm-world/evidence/solid-typed-evidence/routing/effective-access-model.json`.
Directory, permission, serialization, flush, or atomic-replacement failures
stop before stack apply and preserve a previous complete file where one
exists. Do not interpret `result: generated` as evidence that DNS, TLS, HTTP,
Swarm readiness, or login succeeded.

For browser verification, compare the suite summary with the current
`service_access_links`. A missing expected route is reported as `missing` and
fails the suite; disabled optional services are not expected and remain
`service_not_enabled` in routing evidence. Live Selenium is opt-in. Missing
consent, Selenium, or approved credentials should appear as redacted skip
evidence, not as a static-gate failure.

== REFUSED_LIVE_CONSENT_MISSING

Mutating workflow-level commands such as `setup run`, `platform init`,
`platform reconcile`, `platform expose`, `artifacts prepare`, and
`deployment apply` require all
live-consent controls. For the canonical setup path:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live
----

When prompted:

[source,text]
----
Live setup can change local infrastructure. Continue? [y/N]:
----

Answer `y` only when changing local infrastructure is intentional. The
workflow refuses before building application services if `--live` or the
short live confirmation is missing.

This refusal is expected for a plain `setup run` command without consent. It
does not mean the default quality gate failed.

== REFUSED_WORKFLOW_CONFIRMATION_MISSING

`platform reset` and `platform destroy` require exact confirmation:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform reset --confirm RESET_TINY_SWARM_PLATFORM --live
PYTHONPATH=src python3 -m tiny_swarm_world platform destroy --confirm DESTROY_TINY_SWARM_PLATFORM --live
----

After confirmation, reset and destroy act only on configured managed
LXC-native nodes whose Tiny Swarm World ownership evidence is verified before
mutation. Already absent managed nodes are valid reset/destroy evidence.
Missing, mismatched, or unmanaged ownership evidence blocks before deletion.
Do not use these commands as broad Incus cleanup, and do not treat a
confirmation phrase as permission to delete unrelated containers.

If reset reports `managed_nodes_reset_blocked` with
`first_failure_classification=reset_existing_node_not_managed`, a configured
node name already exists but does not fully match the expected Tiny Swarm
World ownership, profile, config, or device safety evidence. The marker
fields may still report `matches` when another safety check blocks mutation.
Inspect the reset evidence for `first_failure_node`,
`first_failure_mismatch_reasons`, and
`first_failure_unsafe_instance_settings` when present. A mismatch reason of
`unsafe_instance_config` means the existing instance has guarded Incus/LXC
config such as `security.privileged=true` without the explicit privileged
ingress override, or a `raw.*` config key. Resolve that named container
manually before rerunning the installer: keep it if it is unrelated,
rename/remove it only if you intentionally own that local resource, or
recreate it through the guarded setup workflow so the managed markers and
expected config are written by automation.

For `first_failure_unsafe_instance_settings: security.privileged`, inspect
both the configured instances and the shared profile. Profile-level
`security.privileged=true` can make every configured node fail the reset
preflight even when each node's ownership markers match:

[source,bash]
----
for node in swarm-manager swarm-worker-1 swarm-worker-2; do
  printf '\n== %s ==\n' "$node"
  incus config get "$node" user.tiny_swarm_world.managed
  incus config get "$node" user.tiny_swarm_world.node
  incus config get "$node" user.tiny_swarm_world.image_alias
  incus config get "$node" security.privileged
done
incus profile get docker-swarm security.privileged
----

Before changing a shared profile, inspect all of its consumers, not just the
three expected TSW nodes:

[source,bash]
----
incus profile show docker-swarm
----

Review its `used_by` entries. If another workload uses the profile, ask the
host operator to isolate or repair the TSW configuration without changing that
workload. Confirm ownership and the intended privileged-ingress policy before
changing any setting. Remove only the diagnosed setting at the specific
instance or profile that owns it; do not unset every location as a batch.

Recheck the guarded preflight afterwards. Run the fresh installer again only
if discarding and recreating the managed environment is intentional; otherwise
use link:usage.adoc#daily-operation[the appropriate operation].

If `raw.*` appears, inspect the exact raw setting on the named instance or
profile and remove only the setting that belongs to disposable Tiny Swarm
World state. Do not use wildcard cleanup for raw Incus/LXC settings.
Direct instance-level `tsw-proxy-<port>` devices are drift. Current
`platform expose` manages equivalent proxy devices in the manager-specific
profile instead of creating direct manager instance devices. If reset reports
`unsafe_instance_devices` for stale direct project proxy devices, first ensure
the manager-profile devices are present, then run the explicit repair command:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform repair-lxc-proxy-drift --live
----

The repair refuses devices whose equivalent manager-profile state is missing
or drifted. Any remaining `unsafe_instance_devices` evidence points to direct
runtime state that must be inspected and resolved intentionally.

== Docker Installation Fails During Platform Init

If live setup stops at `platform init: failed_to_apply`, inspect the setup
evidence for `platform:init:lxc-container-runtime`. When the evidence includes
`first_failure_reason: apt_repository_unreachable`, Tiny Swarm World created
the managed LXC nodes, but Docker Engine installation inside those nodes could
not reach Ubuntu or Docker APT repositories.

Typical evidence:

[source,text]
----
- platform:init:lxc-container-runtime: failed_to_apply
  Evidence:
  - classification: container_runtime_not_verified
  - failed_apply_count: 3
  - failed_nodes: swarm-manager,swarm-worker-1,swarm-worker-2
  - first_failure_classification: docker_install_failed
  - first_failure_node: swarm-manager
  - first_failure_reason: apt_repository_unreachable
----

The Docker registry mirror and the Ubuntu/Docker APT mirrors are separate.
`TSW_LXC_DOCKER_REGISTRY_MIRROR` does not replace `archive.ubuntu.com` or the
Docker APT repository used during Docker Engine installation.

First run the read-only network diagnosis from the same WSL/Linux shell:

[source,bash]
----
./tsw doctor network
----

If setup reaches `artifacts prepare` and times out waiting for Nexus while
`docker service ls` reports `nexus_nexus 1/1`, inspect Docker logs on the node
that runs Nexus. Messages such as `Module ip_vs not found` or `Failed to create
a new service ... operation not permitted` mean Docker Swarm `ingress`/VIP
routing is unavailable in the current WSL2/LXC runtime. Tiny Swarm World's
`wsl2-nat` profile avoids this by publishing external service ports in
`mode: host` on the manager node instead of relying on the Swarm routing mesh.

If the diagnosis reports Docker blocking Incus bridge forwarding, apply only
the targeted forwarding repair:

[source,bash]
----
./tsw network repair --linux-forwarding --apply
----

If outbound internet is intentionally blocked or unreliable, configure APT
mirrors that are reachable from inside the Incus containers. The example below
then performs a *deliberate fresh reset*: use it only when the managed
environment is disposable. To retain existing state, choose a retry through
link:usage.adoc#daily-operation[Daily operation] instead.

[source,bash]
----
export TSW_LXC_UBUNTU_APT_MIRROR=http://<lxc-reachable-host>:8081/repository/ubuntu-apt-proxy
export TSW_LXC_UBUNTU_SECURITY_APT_MIRROR=http://<lxc-reachable-host>:8081/repository/ubuntu-security-apt-proxy
export TSW_LXC_DOCKER_APT_MIRROR=http://<lxc-reachable-host>:8081/repository/docker-apt-proxy
export TSW_LXC_DOCKER_APT_GPG_URL=http://<lxc-reachable-host>:8081/repository/docker-apt-proxy/gpg

./install.sh --headless --confirm-reset --non-interactive-live-approval
----

Use an address reachable from inside the LXC nodes. Do not use `localhost`,
`127.0.0.1`, or a Windows-only address for these mirror URLs.

== Git Shows Line Ending Only Changes

The repository uses `.gitattributes` to normalize text files to LF. If a large
number of files appears modified after switching between Windows Git and WSL,
refresh the checkout with Git after saving any real work.

Do not commit line-ending-only changes unless the change is an intentional
normalization commit.
