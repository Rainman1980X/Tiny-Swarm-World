Tiny Swarm World is developed and operated from a Linux or WSL shell.
Windows-native product execution is not supported. The elevated Windows bridge
prework documented for default WSL2 browser exposure is a supported host setup
step; project automation itself continues to run from Linux or WSL.

== Choose The Right Operation

This page describes a fresh installation. *The installer resets managed Tiny
Swarm World nodes before setup; their data may be lost.* For an existing
environment, start with link:{user-guide-prefix}usage.adoc#daily-operation[Daily operation].
A reset is not a repair step or a product update.

For a first installation, complete the host prerequisites, prepare the Python
environment, then use <<ready-for-install-checklist>>. The default internal-test
path needs no password file. Optional overrides are covered separately below.

RC1 qualification is still in progress. See
https://github.com/MatthiasBurger-Coder/Tiny-Swarm-World/issues/294[the RC1 tracker]
for current acceptance gaps; this procedure is not a claim that every target
and lifecycle has passed.

== Operating Model

Tiny Swarm World prepares a local Docker Swarm target environment on managed
LXC nodes through Incus. The supported operator surface is the
`tiny-swarm-world` CLI and the Linux/WSL `install.sh` wrapper. Multipass and
Windows-native execution are not supported node-provider paths.

== Intended Identity Boundary

Tiny Swarm World is an internal development and test environment tool. The
deterministic catalog values are `INTERNAL/TEST ONLY` material for disposable
local acceptance; unchanged defaults are not suitable for production, shared,
public, or untrusted exposure.

Enterprise identity and reachability remain outside the bootstrap path. AD,
LDAP, SSO, VPN, firewall, network segmentation, and IAM policy are supplied
and governed by the surrounding organization. When stronger or environment-
specific credentials are required, provide them through the documented
protected operator override or applicable Infisical path; do not edit the
catalog or copy passwords into evidence.

== Prerequisites

Install these tools before running project automation:

* Python 3.12 or newer, with virtual-environment support (CI covers 3.12 and 3.13)
* Git
* Incus for the default `lxc_native` node provider
* WSL2 with systemd, cgroup, and user-namespace support when running under WSL
* a WSL Linux-native repository path, preferably
  `/home/<user>/projects/Tiny-Swarm-World`, when running under WSL2
* `socat`, when WSL port forwarding is needed

Optional tools for service preparation:

* `curl`
* `jq`

The default `service-access` profile pulls public base images, including the
Infisical stack image, through the managed node Docker daemon. Repeated
fresh-install runs can hit Docker Hub rate limits. Use authenticated pulls on
the managed node path or provide a reviewed, operator-managed external cache
through `TSW_LXC_DOCKER_REGISTRY_MIRROR`. The former repository helper that
rewrote the host Docker daemon configuration was removed because it bypassed
the governed Python workflow.

The managed Swarm Nexus stack still prepares its own Docker proxy repository
for repository service behavior. Its defaults are:

[source,bash]
----
TSW_NEXUS_DOCKER_HUB_PROXY_REPOSITORY=docker-hub-proxy
TSW_NEXUS_DOCKER_HUB_PROXY_PORT=5001
TSW_NEXUS_DOCKER_HUB_PROXY_REMOTE_URL=https://registry-1.docker.io
----

If Docker Hub already blocks a required image and no local cache is available,
point the image variables at an approved reachable cache before running
`install.sh`:

[source,bash]
----
export TSW_NEXUS_IMAGE=registry.local:5000/sonatype/nexus3:3.75.1
export TSW_INFISICAL_IMAGE=registry.local:5000/infisical:v0.159.1
export TSW_INFISICAL_POSTGRES_IMAGE=registry.local:5000/postgres:14.23-alpine3.23
export TSW_INFISICAL_REDIS_IMAGE=registry.local:5000/redis:7.4.9-alpine3.21
----

== WSL Project Filesystem Policy

On WSL2, clone or place the repository on the distribution's Linux filesystem,
for example below `/home/<user>/projects/Tiny-Swarm-World`. A checkout on a
Windows-mounted filesystem such as `/mnt/c`, `/mnt/d`, or `/mnt/e` is supported
only through an explicit exception and blocks live installation by default.
Tiny Swarm World resolves symlinks and evaluates the longest matching
`/proc/self/mountinfo` entry, including `drvfs` and WSL `9p`/`v9fs` DrvFS
mounts. It does not hard-code one drive letter and does not move or copy the
checkout.

The non-mutating check is part of static preflight immediately after host
classification:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world --preflight
----

The `HOST-FILESYSTEM` result reports only the filesystem classification,
decision, override state, and safe remediation. It never exposes the resolved
project path. An unreadable, contradictory, or unrecognized WSL mount table
fails closed.

When running intentionally from a Windows-mounted checkout, add the exact
override to the installer:

[source,bash]
----
./install.sh --allow-wsl-windows-filesystem
----

The override applies only to a confirmed WSL2 Windows-mounted repository. It
does not permit unsupported hosts or an unknown filesystem. Before the legacy installer's dependency-bootstrap and live workflow phases,
the installer records an applied override in:

[source,text]
----
${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/installation/project-filesystem-decision.json
----

The evidence is an allowlisted schema-v1 JSON document, written atomically
with directory mode `0700` and file mode `0600`. Its target must itself be on a
verified Linux-native or WSL Linux filesystem. A relative `XDG_STATE_HOME`, a
Windows-mounted evidence target, or permissions that cannot be enforced blocks
installation. The exact resolved project path is permitted only in this
protected local document; normal evidence, logs, CLI output, CI artifacts, and
committed files remain path-free.

== Python Environment

Clone the repository if needed, then prepare the runtime from its root:

[source,bash]
----
git clone https://github.com/MatthiasBurger-Coder/Tiny-Swarm-World.git
cd Tiny-Swarm-World
----

If you already have a checkout, enter that directory instead of cloning again.

[source,bash]
----
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install --require-hashes -r requirements.lock
python3 -m pip install --no-deps -e .
----

`requirements.lock` is the audited Python 3.12 runtime set used by CI. The
editable project install deliberately uses `--no-deps` so pip does not resolve
a second runtime dependency set.

Use the active virtual environment for subsequent commands. Runtime imports
are needed before the installer can reach its internal dependency-bootstrap
fallback; do not rely on that fallback to make a bare checkout runnable.

Development tools are optional for operators. Install them before running the
development quality gate:

[source,bash]
----
python3 -m pip install -r requirements-dev.txt
----

== Verify The Development Setup

Run the full quality gate from the repository root:

[source,bash]
----
python3 tools/quality_gate.py quality
----

If a virtual environment is active, its interpreter can be used instead:

[source,bash]
----
.venv/bin/python tools/quality_gate.py quality
----

The quality gate sets `PYTHONPATH=src` automatically.

== Artifact Contract And Readiness Preflight

The selected service profile is the source of the required image inventory.
The default `service-access` profile includes the management-stack images;
use `--service-profile default` when the base profile is intentionally
selected. During `setup run`, the artifact contract preflight runs after the
general preflight and before host or platform mutation. It is non-mutating and
checks the effective Compose image references against the typed image
contracts, immutable tags or digests, duplicate/conflicting targets, and
repository-local build contexts. Build-context inspection crosses the
`PortLocalFileStorage` application port; filesystem details remain in the
infrastructure adapter.

After deployment bootstrap, the setup artifact path runs the required artifact
bootstrap, then the bounded readiness gate, and only then `artifacts prepare`
and `artifacts verify`. The readiness gate observes manager Docker, registry
and Nexus endpoints/repositories, manager storage, build inputs, and the
public pull prerequisite. Every observation uses a five-second timeout and one
attempt by default. A failed, unknown, partial, degraded, or unavailable
mandatory result stops image mutation and dependent deployment phases.

Static contract checks and the default quality gate never call Docker, Incus,
Swarm, registry or Nexus infrastructure. The readiness phase is live and
requires the normal explicit live-consent contract. A local test or configured
endpoint is not live evidence; only redacted evidence from an authorized run
may be reported as `LIVE_VERIFIED`.

During `setup run`, the executable order is: host preparation and verification,
managed-node `platform init` and `platform reconcile`, `cluster docker`,
`cluster swarm bootstrap`, `cluster verify`, routing exposure, and then the
artifact and deployment phases. `platform init` does not install Docker or
initialize Swarm; the cluster phases own those operations. If a cluster phase
is blocked or fails, later routing, artifact, and deployment phases are marked
`not_run`.

The operator-facing installation order is therefore:

. prepare and verify the Linux/WSL host and the Incus daemon;
. select and verify the managed `lxc_native` provider resources;
. create or reconcile the three configured managed LXC nodes;
. install or verify Docker Engine *inside* those managed nodes;
. initialize and verify Docker Swarm inside the managed nodes;
. expose the configured routing/proxy boundary;
. prepare artifacts, apply selected service stacks, and verify readiness.

Host Docker is not the workload runtime for this path. A host Docker CLI may
be installed for diagnostics, local cache helpers, or evidence probes, but the
setup workflow installs and verifies the service workload Docker Engine inside
the Incus-managed nodes. Do not interpret `docker info` on the host as proof
that node-local Docker or Swarm is ready; use the managed-node checks in the
runtime verification section.

== LXC Native Provider Baseline

=== Hard Host Prerequisite Boundary

The default provider is `lxc_native` through the managed Incus backend. An
Incus/LXD host management layer is therefore a hard prerequisite before a live
Tiny Swarm World run. Incus/LXD installation, daemon initialization, storage
pool and bridge creation, profile changes, daemon repair, and group membership
are host-operator responsibilities. Tiny Swarm World does not install or
initialize Incus/LXD automatically.

From the same Linux/WSL shell that will run `./install.sh`, the current user
must be able to run the provider client without `sudo`:

[source,bash]
----
incus version
incus info
----

If the host operator changed `incus-admin` or another provider-access group,
close and reopen the shell before running these checks. Do not hide a missing
permission behind `sudo`; the installer and preflight must observe the same
user-level access that the live workflow will use.

The ready-for-install checklist below is the operator path. The technical
provider boundary and optional target-specific smoke are maintained in
`documentation/system/lxc-native-setup.adoc`.

Backend selection first honors an explicit `--lxc-backend incus` override,
then `backend_selection.preferred_backend` in
`infra/config/node-providers/provider_config.yaml`.

Backend resource names are configured under
`provider_resource_resolution.backends.<backend>`. The committed defaults map
Incus `control` traffic to `incusbr0` with `default` as the storage pool.
Override the Incus section before live setup when the local network bridge or
storage pool uses a different name.

For Incus, follow the official installation instructions for the host
distribution, then verify access from the same shell:

[source,bash]
----
incus version
incus info
----

Run the project preflight before live mutation:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world --preflight
PYTHONPATH=src python3 -m tiny_swarm_world --lxc-backend incus --preflight
----

The live `setup run` sequence performs `host prepare` and read-only `host
verify` after preflight and before Incus initialization. To prepare the
Windows/WSL bridge independently, use the dedicated host command and provide
the explicit live consent flags. If WSL does not expose the canonical
ProgramData location at `/mnt/c`, set `TSW_WINDOWS_WSL_BRIDGE_STATE_PATH` to
the protected bridge-state file before running preflight.

See `documentation/system/lxc-native-setup.adoc` for the full WSL2 and
Incus setup notes and official references.

[[ready-for-install-checklist]]
== Ready-For-Install Checklist

Complete this checklist from the same Linux/WSL shell that will run
`./install.sh`. The first items are static/read-only checks. The optional
temporary-container smoke is a small live provider check and requires explicit
operator approval; it is not part of the repository quality gate.

* [ ] The shell is native Linux or WSL2 with the required systemd/cgroup/user-
  namespace capabilities.
* [ ] The repository is on a Linux-native path when running under WSL2, or the
  explicit filesystem override is intentionally approved.
* [ ] Incus is installed and initialized by the host operator; the current user
  runs `incus version` and `incus info` without `sudo`.
* [ ] The selected Incus storage pool, network bridge, and required profile
  state are available to that same user.
* [ ] Python dependencies are installed and `python3 tools/quality_gate.py
  quality` is green when local development verification is required.
* [ ] `PYTHONPATH=src python3 -m tiny_swarm_world --preflight` passes its static
  checks before any live consent is supplied.
* [ ] The standard internal-test catalog is selected, or intentional overrides
  are available from the protected source described below. The default path
  requires no credential file.
* [ ] The managed environment is disposable or its needed data is backed up;
  the fresh installer will run a reset before setup.
* [ ] For WSL2 Windows-browser access, the required Windows bridge is ready.
  Native Linux does not need that bridge.

The detailed optional smoke appears in the Incus baseline below. After this
checklist, continue with the ordered runtime path: host preparation and
verification, managed LXC nodes, Docker Engine inside those nodes, Swarm
bootstrap, routing, artifacts, deployment, and final verification.

== Runtime Environment Green Path

Use this checklist when preparing a new developer workstation for the default
local runtime environment. Run project commands from a Linux or WSL shell in
the repository root. The browser can run on the host operating system, but the
automation commands remain Linux/WSL commands.

=== 1. Verify The Host Shell

Confirm that the shell is Linux or WSL2 and that the repository is reachable
through a Linux path. Under WSL2, prefer a path below the Linux home directory:

[source,bash]
----
pwd
uname -a
python3 --version
git status --short --branch
----

When using WSL, verify that systemd is available:

[source,bash]
----
systemctl is-system-running || true
cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null || true
----

`unprivileged_userns_clone` should be `1` when the file exists. If group
membership was changed for Incus access, close and reopen the shell before
continuing.

=== 2. Prepare Python Dependencies

Complete <<_python_environment,Python Environment>> once per checkout, then
activate `.venv` in each new shell. Development verification is a separate step;
install `requirements-dev.txt` before running its quality gate.

=== 3. Verify Incus Baseline And Optional Smoke

The default provider is Incus-backed `lxc_native`. Verify the daemon first.
The temporary-container smoke below is optional and changes provider state;
run it only when that isolated test and its cleanup are intentional:

[source,bash]
----
incus version
incus info
incus launch images:ubuntu/24.04 test-incus
incus exec test-incus -- cat /etc/os-release
incus delete test-incus --force
----

Run the temporary-container block only when a live provider smoke is approved.
If `incus launch` succeeds but a later command fails, delete the named
`test-incus` container before retrying. Do not use broad container cleanup.

The normal project setup creates and owns the managed nodes. Do not manually
create `swarm-manager`, `swarm-worker-1`, or `swarm-worker-2` unless a
documented recovery step tells you to do so.

=== 4. Prepare Kernel And Bridge Networking

Tiny Swarm World reads the native Linux kernel controls during host preparation
and verification, but never changes operator-owned kernel state. The check
fails closed when a required control is missing, disabled, or unreadable. Its
evidence contains only the stable control name and one of `active`, `missing`,
`disabled`, or `read_error`; it does not record the observed value or procfs
path.

If the native Linux check is not ready, the host operator can temporarily load
bridge netfilter and activate the required controls for the current boot:

[source,bash]
----
sudo modprobe br_netfilter 2>/dev/null || true
sudo sysctl -w net.bridge.bridge-nf-call-iptables=1
sudo sysctl -w net.bridge.bridge-nf-call-ip6tables=1
sudo sysctl -w net.ipv4.ip_forward=1
----

These commands mutate host state and therefore remain outside Tiny Swarm World
automation. Run them only after reviewing them for the host. Temporary
activation is not persistent and Tiny Swarm World does not claim to roll it
back during cleanup.

Separately configure persistence when the host supports `sysctl.d`:

[source,bash]
----
sudo tee /etc/sysctl.d/99-tiny-swarm-world.conf >/dev/null <<'EOF'
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
EOF
sudo sysctl --system
----

The persistence file is operator-owned. Remove or change it only through the
host's normal administration process; Tiny Swarm World cleanup leaves it
untouched.

After either temporary activation or persistence, inspect the effective
controls directly. The next explicitly authorized `setup run --live` also
rechecks them before later setup phases:

[source,bash]
----
sysctl net.ipv4.ip_forward
sysctl net.bridge.bridge-nf-call-iptables
sysctl net.bridge.bridge-nf-call-ip6tables
----

Docker Swarm overlay networking uses VXLAN. On WSL, `lsmod` may not show a
separate `vxlan` module even when VXLAN links can be created. Use a temporary
link test instead:

[source,bash]
----
DEFAULT_IFACE="$(ip route show default | awk '{print $5; exit}')"
sudo ip link add vxlan-test type vxlan id 42 dev "$DEFAULT_IFACE" dstport 4789
echo "vxlan_create=$?"
ip link show vxlan-test
sudo ip link delete vxlan-test
----

`vxlan_create=0` confirms that the kernel path is usable for the local Swarm
overlay test. Remove the test link immediately as shown above.

On native Linux hosts with a restrictive firewall, allow bridge-internal
traffic on the Incus control bridge before rerunning setup:

[source,bash]
----
sudo iptables -I FORWARD 1 -i <backend-bridge> -o <backend-bridge> -j ACCEPT
----

Replace `<backend-bridge>` with the bridge resolved from
`provider_resource_resolution.backends.<backend>.network_mappings.control`.

[[operator-credential-overrides]]
=== 5. Optional Operator Credential Overrides

The standard internal-test path requires no credential preparation. It resolves
the deterministic `INTERNAL/TEST ONLY` catalog values documented in the
canonical link:{user-reference-prefix}arc42/08_configuration/internal-test-credential-catalog.md[credential catalog]
and prints service targets after a successful run without printing passwords.
Copy `.env.example` only when you need to provide an explicit operator
override:

[source,bash]
----
install -d -m 700 "$HOME/.local/state/tiny-swarm-world"
export TSW_INSTALL_ENV_FILE="$HOME/.local/state/tiny-swarm-world/live-installation.env"
# Copy only for a new override file; preserve an existing file.
if [ ! -e "$TSW_INSTALL_ENV_FILE" ]; then
  (umask 077; cp .env.example "$TSW_INSTALL_ENV_FILE")
fi
chmod 600 "$TSW_INSTALL_ENV_FILE"
----

Use a private editor to set only the overrides you intend; leave other entries
empty to use the catalog. The file and its immediate directory must belong to
your effective user and group, with modes `0600` and `0700` respectively.
Do not use symlinked files/directories. Keep this location Linux-native even
when the source checkout is under `/mnt/*`. Export `TSW_INSTALL_ENV_FILE` again
in a new shell so the installer selects the same file. This file is an optional operator override input; the normal installer resolves all other
values from the catalog and does not generate or rotate credential files. Do
not paste values from it into logs, issues, chat, commits, or documentation.

For an authorized WSL2 live run from a checkout under `/mnt/<drive>`, set
`TSW_INSTALL_ENV_FILE` to a WSL-native `0600` file outside the checkout and
keep live evidence under a verified WSL-native `0700` root. The source-tree
override does not make a mounted Windows filesystem safe for credentials. See
`documentation/evidence/wsl2-secure-live-path.md` for the complete procedure.

Important login-related keys include:

* `TSW_PORTAINER_USERNAME`
* `TSW_PORTAINER_ADMIN_PASSWORD`
* `TSW_PULSAR_ADMIN_TOKEN`
* `TSW_PULSAR_MANAGER_ADMIN_PASSWORD`

Use the catalog for default login details and the protected source for explicit
overrides. Dashboard references do not prove that service values have been
synchronized into Infisical. The current self-hosted workflow rejects external
Infisical mode; see
link:{user-reference-prefix}arc42/08_configuration/credential-source-precedence.md[credential source precedence].

=== 6. Configure Local Route Names

Traefik owns local HTTP and HTTPS ingress on ports `80` and `443`. Hostname
resolution must map the routed names to the local machine; DNS does not route
traffic by itself. It only makes the browser send the correct host name to
Traefik.

Prometheus, Grafana, app, and API host routes are conditional. They appear in
the generated access model, dashboard, health targets, and browser matrix only
when the corresponding service is enabled by the selected configuration.

[[windows-wsl-prework]]
==== Complete The Required Windows Prework For WSL2

When running Tiny Swarm World in WSL2 with the default Windows exposure, prepare
the Windows side *before* starting `./install.sh`. The installer deliberately
stops before platform mutation when this bridge is missing, degraded, or stale.

First confirm from Windows PowerShell that the intended WSL2 distribution is
running and uses `systemd` as PID 1:

[source,powershell]
----
wsl --list --verbose
wsl -d <DistributionName> --exec sh -lc "ps -p 1 -o comm="
----

The second command must print `systemd`. Then open *PowerShell as
Administrator* in the Tiny Swarm World repository root. If this is not the
Windows default WSL distribution, first set its exact name in
`tools/windows/tws-wsl-bridge.config.json` instead of keeping the automatic
`"distro": "auto"` selection. Then run:

[source,powershell]
----
Set-ExecutionPolicy -Scope Process Bypass
.\tools\windows\tws-wsl-bridge.ps1 -Action prerequisites
.\tools\windows\tws-wsl-bridge.ps1 -Action install
----

The first service installation opens a Windows credential dialog. Use the
Windows account that owns the WSL distribution and enter its normal Windows
password, not the Windows Hello PIN. The password is passed to the Windows
Service Control Manager and is not stored in the repository.

Installation publishes a protected runtime bundle below
`%ProgramData%\TinySwarmWorld\WslBridge`; the service does not execute mutable
files directly from the checkout. Re-run the elevated `-Action install` after
reviewed bridge, configuration, or port-registry changes to upgrade that
bundle.

The protected heartbeat is stored at
`%ProgramData%\TinySwarmWorld\WslBridge\bridge-state.json` and read from WSL via
`/mnt/c/ProgramData/TinySwarmWorld/WslBridge/bridge-state.json`. The service does
not write a checkout mirror. Hosts with a non-default WSL automount must expose
the canonical ProgramData location before live setup.

The tracked default uses `"listenAddress": "0.0.0.0"` and managed inbound
Firewall rules, so its listeners are not limited to Windows loopback. Review
the bridge configuration and Windows network profile before installation when
the host is connected to an untrusted network.

Verify the completed prework before returning to the WSL shell:

[source,powershell]
----
Get-Service -Name TinySwarmWorldWslBridge
.\tools\windows\tws-wsl-bridge.ps1 -Action status
----

The service must report `Running`, and bridge discovery must report `READY`.
The service then keeps the Windows portproxy, Firewall, `*.tsw.local` hosts
entries, and current WSL address aligned automatically.

Only when Windows browser and localhost exposure are intentionally not needed,
disable that contract explicitly in the WSL shell before installation:

[source,bash]
----
export TSW_WINDOWS_EXPOSURE=disabled
----

See `tools/windows/README.windows-wsl-bridge.md` for distro selection, repair,
status, verification, and uninstall details.

==== Linux Shell Name Resolution

For WSL/Linux shell checks, add the routed names to `/etc/hosts`. If a
matching `tsw.local` line already exists, update that line instead of adding
duplicates:

[source,bash]
----
sudo tee -a /etc/hosts >/dev/null <<'EOF'
127.0.0.1 service-access.tsw.local portainer.tsw.local nexus.tsw.local jenkins.tsw.local pulsar.tsw.local pulsar-api.tsw.local sonarqube.tsw.local swagger.tsw.local infisical.tsw.local
EOF
----

For Windows browsers, use the managed bridge configured above. The bridge
maintains the Windows host entries; do not add a second competing set.
Name resolution alone does not establish forwarding, TLS trust or service health.

=== 7. Run The Fresh Install

*This step resets the managed environment before installation.* Complete the
checklist above and preserve needed data first. Use the default
`service-access` profile for the full local runtime. The
current LXC Swarm ingress path requires an explicit privileged-ingress opt-in
when the managed Incus profile needs privileged Swarm settings:

[source,bash]
----
export TSW_LXC_ALLOW_PRIVILEGED_SWARM_INGRESS=1
./install.sh --headless --confirm-reset --non-interactive-live-approval
----

Without `--headless`, the installer uses the interactive terminal recorder.
Without `--confirm-reset`, it asks for the exact reset phrase before the
fresh-install reset. Without `--non-interactive-live-approval`, it asks the
normal live-infrastructure confirmation prompt.

The wrapper first runs:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform reset --live --confirm RESET_TINY_SWARM_PLATFORM --service-profile service-access
----

Only after reset succeeds does it run:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live --service-profile service-access
----

The run writes evidence under
`${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/evidence/installation-tests/<host-runtime>/<UTC timestamp>/`
by default. If `TSW_LIVE_EVIDENCE_ROOT` is set, it selects the root before
`<host-runtime>/<UTC timestamp>/` is appended. The root and run directories
must be protected Linux-native storage. Use the exact directory printed by
the installer; old checkout-local evidence is historical.
Use `reset-run.exit`, `setup-run.exit`, and the matching logs to diagnose a
failed or blocked run.

Before stack apply, the deployment workflow also writes the selected effective
access model to
`.tiny-swarm-world/evidence/solid-typed-evidence/routing/effective-access-model.json`.
This redacted file contains configured routing evidence and only credential
labels plus Infisical item references. Its `result: generated` value does not
prove that a route is deployed or reachable.

The cluster boundary is verified before routing or deployment continues. The
Docker phase checks every configured managed node. The Swarm bootstrap phase
initializes the manager before any worker join and refuses a missing or
unavailable worker credential. The cluster verification phase reads structured
membership from the managed manager and requires all expected nodes to be
observed as Docker `Ready` and `Active`, with the manager in `Leader` state.
These checks are live-operation behavior; this guide does not claim that they
have passed on a live host without matching redacted `LIVE_*` evidence.

=== 8. Verify The Runtime

Start with the non-mutating workflow, keeping the installed service profile:

[source,bash]
----
tiny-swarm-world --service-profile service-access platform verify
----

Then verify the managed nodes and Swarm state:

[source,bash]
----
incus list --format compact
incus exec swarm-manager -- docker node ls
incus exec swarm-manager -- docker stack ls
incus exec swarm-manager -- docker service ls
----

Then check routed service reachability from the same environment where the
browser will run. The following `-k` probes deliberately skip certificate
verification; they are diagnostic HTTP checks only, not TLS or login acceptance.
Repeat the required checks without `-k` once the configured CA is trusted, and
verify actual authenticated access separately:

[source,bash]
----
curl -k -sS -o /dev/null -w 'service-access %{http_code}\n' https://service-access.tsw.local/
curl -k -sS -o /dev/null -w 'portainer %{http_code}\n' https://portainer.tsw.local/
curl -k -sS -o /dev/null -w 'nexus %{http_code}\n' https://nexus.tsw.local/
curl -k -sS -o /dev/null -w 'jenkins %{http_code}\n' https://jenkins.tsw.local/login
curl -k -sS -o /dev/null -w 'pulsar-manager %{http_code}\n' https://pulsar.tsw.local/
curl -k -sS -o /dev/null -w 'pulsar-api %{http_code}\n' https://pulsar-api.tsw.local/admin/v2/clusters
curl -k -sS -o /dev/null -w 'sonarqube %{http_code}\n' https://sonarqube.tsw.local/api/system/status
curl -k -sS -o /dev/null -w 'swagger %{http_code}\n' https://swagger.tsw.local/
curl -k -sS -o /dev/null -w 'infisical %{http_code}\n' https://infisical.tsw.local/
----

For authentication-protected endpoints, `401`, `403`, or a login page can be
valid reachability evidence. For the Pulsar Admin API, a request without the
bearer token should be treated as a route/authentication check, not as a
service failure. For an authenticated check, obtain the effective token privately
from its configured source and use an approved private API client that does not
expose the token in shell history, process arguments or shared diagnostics.
Do not source the optional override file unconditionally: a default installation
does not create that file, and an empty placeholder is not a resolved token.
A successful authenticated cluster-list response should include `standalone`.
A login page or HTTP 200 from Jenkins likewise does not prove authentication.

=== 10. Re-run And Recovery Rules

Start with read-only verification and classify the first failed phase.
Use link:{user-guide-prefix}usage.adoc#daily-operation[Daily operation] to choose between platform
reconciliation, broader setup without a preliminary reset, and a deliberate
fresh reset. Reuse the same service profile and effective configuration.

Do not rerun `./install.sh` merely to repair one service: it always includes a
fresh reset. The current revision has no supported `./install.sh --update`;
a canonical product update and its cross-host acceptance remain tracked in
https://github.com/MatthiasBurger-Coder/Tiny-Swarm-World/issues/297[#297].

If a developer intentionally needs to discard the managed local environment,
use the governed reset path rather than deleting arbitrary Incus resources:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform reset --live --confirm RESET_TINY_SWARM_PLATFORM --service-profile service-access
----

If direct `tsw-proxy-*` instance devices block reset or expose operations,
repair only the reviewed Tiny Swarm World proxy drift:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform repair-lxc-proxy-drift --live
----

Do not commit `.tiny-swarm-world/`, `.tiny-swarm/`, `.venv/`, coverage files,
or any local secret file.

== Repository Runtime Model

Python source code lives under `src/tiny_swarm_world` and uses package imports
such as `tiny_swarm_world.application...`,
`tiny_swarm_world.domain...`, and `tiny_swarm_world.infrastructure...`.
Install the repository in editable mode from a Linux or WSL shell before
operator runs:

Example:

[source,bash]
----
python3 -m pip install --no-deps -e .
tiny-swarm-world
----

Manual source-checkout commands can still use
`PYTHONPATH=src python3 -m tiny_swarm_world`. `tools/quality_gate.py` sets the
needed source path for repository checks.

List supported workflow-level commands without building application services:

[source,bash]

tiny-swarm-world --list-workflows
----

== IntelliJ Execution Context

IntelliJ is supported as a Linux/WSL shell surface for this project. Configure
the run configuration to use the WSL or Linux Python interpreter, repository
root working directory, and the same environment that passes the shell
preflight checks. The command remains:

[source,bash]
----
tiny-swarm-world setup run --live
----

The live confirmation prompt requires stdin. Run the command from an IntelliJ
terminal or a run configuration that can answer the prompt. This does not add
Windows-native execution support.

The safe setup probe is:

[source,bash]
----
tiny-swarm-world setup run
----

Without the complete live-consent contract, `setup run` refuses before setup
services are constructed and prints `REFUSED_LIVE_CONSENT_MISSING`. This is
the expected safe default.

The canonical live operator command uses `lxc_native` by default:

[source,bash]
----
tiny-swarm-world setup run --live
----

For a deliberate fresh reset and installation with local evidence capture, use:

[source,bash]
----
./install.sh
----

`install.sh` is intentionally a minimal Linux/WSL bootstrapper. The
authoritative installer policy is `python3 -m tiny_swarm_world.simple_installer`:
that Python entry point owns secret handling, host-runtime detection, evidence
layout, reset/setup sequencing, dependency bootstrap, and headless
execution. The shell wrapper only verifies the repository shape and delegates.

For deliberate test-system automation, the wrapper confirmation prompt can be
replaced by an explicit flag:

[source,bash]
----
./install.sh --confirm-reset
----

The CLI live-infrastructure prompt is separate from the reset prompt. Normal
wrapper runs keep that prompt interactive inside the terminal recorder. For
deliberate non-interactive automation, pass an explicit live-approval flag:

[source,bash]
----
./install.sh --non-interactive-live-approval
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live --approve-live
----

The automation flag is an approval source; it does not remove the `--live`
requirement.

Terminal recording is optional presentation. For headless systems that cannot
or should not start the terminal recorder/TUI surface, use:

[source,bash]
----
./install.sh --headless
TSW_INSTALL_HEADLESS=1 ./install.sh
----

Headless mode executes the same governed reset and setup commands, writes the
same `reset-run.log`, `reset-run.exit`, `setup-run.log`, and `setup-run.exit`
evidence files, and preserves command exit codes.

The wrapper writes run context, reset logs, setup logs and exit codes below
`${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/evidence/installation-tests/<host-runtime>/<UTC timestamp>/`
by default. If `TSW_LIVE_EVIDENCE_ROOT` is set, it selects the root before
`<host-runtime>/<UTC timestamp>/` is appended. The root and run directories
must be protected Linux-native storage. Use the exact directory printed by
the installer; old checkout-local evidence is historical.
The stable host directory is `wsl2` for WSL2 and `native_linux` for native
Linux. The run `context.txt` records `host_runtime_type`,
`host_runtime_detection_source`, `selected_evidence_directory`,
`live_execution_mode`, `live_approval_source`, and `terminal_recording_mode`
alongside `reset-run.log`, `reset-run.exit`, `setup-run.log`, and
`setup-run.exit`.
It resolves catalog-backed `TSW_*` credentials and optional operator overrides
without printing secret values. It does not generate a local credential file.
Required local bootstrap values are derived from
`infra/config/secrets/infisical-secrets.yaml`; installer code does not maintain
a separate required-secret list.
The default path requires no credential file. For intentional overrides, follow
<<operator-credential-overrides>>; the process environment takes precedence
over file values. Static checks validate configuration, not service login.
After the Python entry point has imported successfully, its internal fallback
can prepare missing subprocess dependencies in an ignored local environment at
`.tiny-swarm-world/install-venv` and uses its Python interpreter for the reset
and setup commands. That bootstrap installs the lock with hash verification,
then installs the editable project without resolving dependencies again. WSL
keeps the existing `python3` execution path when the required imports are
already available.
Ensure the current shell can access the Incus daemon before running
`install.sh`; reopen the shell after group membership changes when required by
the host distribution.

On native Linux, Docker Swarm also requires that the managed LXC containers can
reach each other on the selected backend bridge. Use the bridge name resolved
from `provider_resource_resolution.backends.<backend>.network_mappings.control`
when applying host firewall rules. If workers can reach the configured bridge
gateway but cannot ping the manager container or connect to Swarm port `2377`,
allow bridge-internal forwarding on the host:

[source,bash]
----
sudo iptables -I FORWARD 1 -i <backend-bridge> -o <backend-bridge> -j ACCEPT
----

Verify the host firewall path before rerunning installation. Replace the
manager address with the current manager container address from
`incus list` or `incus exec swarm-manager -- hostname -I`:

[source,bash]
----
incus exec swarm-worker-1 -- ping -c 2 <manager-ip>
incus exec swarm-worker-1 -- nc -vz <manager-ip> 2377
----

If `ufw` manages the host firewall, persist the bridge route rule with:

[source,bash]
----
sudo ufw route allow in on <backend-bridge> out on <backend-bridge>
sudo ufw reload
----

On hosts that use persistent iptables rules directly, save the accepted
FORWARD rule after validating it:

[source,bash]
----
sudo apt install iptables-persistent
sudo netfilter-persistent save
----

Swarm bootstrap needs container-to-container access for `2377/tcp`, and later
Swarm traffic uses `7946/tcp`, `7946/udp`, and `4789/udp`. The bridge-internal
FORWARD rule above allows that managed backend-node traffic on the configured
bridge.

Portainer stack create and update calls can take longer than ordinary API
lookups while Docker Swarm pulls images or reconciles services. The installer
uses a longer Portainer stack operation timeout by default. On especially slow
hosts, raise it before an explicitly intended fresh reset, or use the
non-reset setup path in link:{user-guide-prefix}usage.adoc#daily-operation[Daily operation]:

[source,bash]
----
export TSW_PORTAINER_STACK_REQUEST_TIMEOUT_SECONDS=300
./install.sh --confirm-reset
----

Installer-side Python environment bootstrap commands are also bounded. The
default per-command limit is 900 seconds and can be lowered or raised through
the explicit environment setting below; a timeout is reported as a timeout
error and does not silently continue:

[source,bash]
----
export TSW_INSTALL_SUBPROCESS_TIMEOUT_SECONDS=900
----

`install.sh` is a fresh-install entry point. It first calls the governed
destructive reset workflow:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform reset --live --confirm RESET_TINY_SWARM_PLATFORM
----

The wrapper passes the selected service profile to reset and setup. The
default is `service-access`, so the effective reset command is:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform reset --live --confirm RESET_TINY_SWARM_PLATFORM --service-profile service-access
----

Only after reset succeeds does it call the canonical live setup workflow:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live --service-profile service-access
----

If reset is blocked or fails, setup is not started and the script exits with
the reset exit code. The reset scope is intentionally narrow: it may discard
only the managed Tiny Swarm World local system, such as configured LXC-native
provider nodes or marker-verified project-owned instances. It must not delete
all host Incus containers or unrelated provider resources.

== Live Infrastructure Warning

The canonical setup workflow and some legacy helper areas can create or delete
provider nodes or virtual machines, change networking, install Docker, or
deploy stacks. Run live automation only when you intend to change local
infrastructure state. Former direct preparation helpers
and host-side compose
orchestration scripts have been retired.
The canonical classification for these live-operation surfaces is
`documentation/system/live-operation-surfaces.adoc`.

Mutating workflow-level commands such as `platform init`, `platform reconcile`,
`cluster docker`, `cluster swarm bootstrap`, `platform expose`, `platform
repair-lxc-proxy-drift`, `artifacts prepare`, `deployment apply`, and `setup
run` require:

* `--live`;
* answering `y` at the short live-infrastructure confirmation prompt.

`platform reset` and `platform destroy` additionally require their exact
confirmation phrases. `install.sh` asks for
`RESET_TINY_SWARM_PLATFORM` before it runs the reset prelude unless the
operator supplies `--confirm-reset`. The flag confirms only the wrapper prompt;
the reset prelude still calls `platform reset --confirm
RESET_TINY_SWARM_PLATFORM`.

== LXC Proxy Drift Repair

`platform expose` configures published setup-manifest ports as profile-level
proxy devices in the manager-specific `docker-swarm-manager` profile. The
`swarm-manager` node receives that profile in addition to the common Docker
Swarm profile. Worker nodes do not receive the manager proxy profile.

Direct instance-level `tsw-proxy-*` devices on `swarm-manager` are not expected
normal state. They are treated as `unsafe_instance_devices` drift so normal
install, reset, reinstall, init, reconcile, expose and setup flows stop rather
than silently deleting local provider state.

When the manager-profile proxy devices are already present and verified, a
stale direct project proxy can be repaired explicitly:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform repair-lxc-proxy-drift --live
----

Answer `y` only when removing stale direct `tsw-proxy-*` devices from the
manager is intentional. The repair refuses unrelated devices, unknown project
proxy names, and direct project proxy devices whose equivalent
manager-profile device is missing or drifted. It reports summary counts for
removed, refused, lookup-failed and removal-failed devices without printing raw
provider command output.

Optional live smoke validation is separate from the default quality gate. Run
it only on a disposable or recoverable local environment after reviewing the
live-operation surface catalog:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live
----

When prompted, answer `y` only if changing the local Incus/LXC provider
state, Docker Swarm, networking, Portainer, Nexus,
Jenkins, Apache Pulsar, SonarQube, and Swagger/NGINX environment is intentional.

== Service Access Management Prerequisites

The full guided setup includes the service-access management stack with a
dashboard asset rendered from the effective service-access model and
service-access NGINX assets. The setup CLI selects this profile by default.
Operators who intentionally want only the older base service set can pass
`--service-profile default`.

The service-access setup profile exposes Traefik ingress ports `80` and `443`
through the LXC/WSL exposure workflow. The service-access NGINX compose
service publishes registry-backed dashboard port `10000` and explicit
compatibility/rollback port `8086` as stack metadata parsed from
`infra/config/compose/service-access/docker-compose.yml`. The Compose target
ports remain the image-compatible internal ports. WSL `localhost` forwarding
is a separate host-network concern. Endpoint defaults are configuration hints,
not service-health evidence, and local effective-port evidence is not live
readiness evidence. If localhost forwarding is stale, use the current Swarm
node IP only for manual diagnosis until the forwarding issue is repaired.

The service-access dashboard is a generated management table. It lists
service links, users and Infisical item references from the effective access
model; password values are visible only through the configured
secret-management surface. Preferred links use routed HTTPS URLs without the
diagnostic ports `10080` or `10443`. Runtime renderer output is authoritative;
the committed `infra/config/compose/service-access/dashboard/index.html` is a
default-profile fallback/image asset guarded by a renderer drift test, and the
dashboard Dockerfile packages it into the default `service-access` setup path.
