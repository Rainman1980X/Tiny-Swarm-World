Tiny Swarm World contains two different kinds of workflows:

* development workflows that are safe to run during normal coding
* live infrastructure workflows that change Incus/LXC provider state,
  Docker, Portainer, Nexus, networking, or service stacks

Use a Linux or WSL shell from the repository root unless a command explicitly
states otherwise.

[[daily-operation]]
== Daily Operation

Activate the Python environment before using the installed CLI:

[source,bash]
----
source .venv/bin/activate
tiny-swarm-world --service-profile service-access platform verify
----

Replace `service-access` if you installed a different profile. Keep the same
backend and effective configuration used for installation. If the source is
intentionally on a WSL Windows mount, the applicable commands also need
`--allow-wsl-windows-filesystem`.

[options="header"]
|===
| Goal | Command or next step | Effect
| Inspect current platform | `platform verify` | Read-only checks; does not repair.
| Reconcile managed platform | `platform reconcile --live` | Mutates managed platform state; does not constitute a full service update.
| Run the broader setup again | `setup run --live` | Mutates infrastructure and services without the wrapper's preliminary reset.
| Recreate a disposable environment | `./install.sh` | Resets managed state before fresh setup.
| Upgrade a running installation | `platform update --stack ... --service ... --from-image ... --to-image ...` | Preview first; requires live consent and preserves rollback metadata.
|===

For an intentional platform reconciliation, followed by verification:

[source,bash]
----
tiny-swarm-world --service-profile service-access platform reconcile --live
tiny-swarm-world --service-profile service-access platform verify
----

Run the verification only after reconciliation succeeds; on failure, diagnose
the first failed phase before any further mutation.

If the broader setup workflow is required, review its changes and configuration
before using:

[source,bash]
----
tiny-swarm-world --service-profile service-access setup run --live
----

The direct CLI is a separate entry point. Do not assume it inherits the
installer wrapper's resolved credentials or the environment of an earlier
process. Ensure its effective configuration is supplied through the supported
operator contract; if prerequisites are missing, diagnose them rather than
using the reset wrapper as a workaround. See
link:{user-reference-prefix}arc42/08_configuration/operator-configuration-contract.md[the operator contract].

After changes, verify routes and actual logins as described in
link:{user-guide-prefix}installation.adoc#verify-installed-runtime[Verify the runtime].
Platform readiness or a login page alone is not authenticated acceptance.

The supported update is a single existing stack service image transition. A
preview validates image references and configured stack/service membership
without mutation or runtime observation; it does not qualify the running image:

[source,bash]
----
PYTHONPATH=src python3 -m tiny_swarm_world platform update \
  --stack jenkins --service jenkins \
  --from-image 127.0.0.1:13500/jenkins:0.2.0 \
  --to-image 127.0.0.1:13500/jenkins:0.3.0 --preview --json
----

Apply the reviewed transition with `--live --approve-live`. The command
qualifies the observed source image, records the original transition as
protected recovery metadata, and applies the selected stack through the
deployment port. Success requires the service and all active tasks to converge
to the target image in a stable rollout. Missing observations or failed, mixed,
paused or otherwise unconverged rollouts do not count as success. An already
converged target is a verified no-op without deployment or metadata replacement.

Use `platform update --recover --stack jenkins --service jenkins --preview`
to preview recovery, then replace `--preview` with `--live --approve-live` to
apply it. Recovery retains the original transition across failures and retries;
repeating completed recovery is a verified no-op. This metadata is not a backup
of persistent service data and does not restore that data.

Update and recovery do not rewrite configured desired state, which can differ
from the observed running image. Explicitly align effective image configuration
with the image you intend to keep before a later deployment. `platform reconcile`
is a separate explicit platform-state operation; it currently ensures provider
nodes and does not redeploy stack images. Reset remains the deliberate fresh
environment operation.

[[open-the-services]]
== Open The Services

The default full setup uses the `service-access` profile. After a verified
deployment, use the Service Access landing page as the operator start page:

[source,text]
----
https://service-access.tsw.local
----

The dashboard is generated from the selected configuration. Its links are
access targets, not proof of deployed, healthy or authenticated services.
Open the page from the browser you intend to use; that browser's host must
resolve the names, reach the forwarded ports and trust the configured TLS CA.

Common preferred local service routes are:

[options="header"]
|===
| Service | Preferred route | Notes
| Service Access | `https://service-access.tsw.local` | Generated management table with service links and Infisical item references.
| Infisical | `https://infisical.tsw.local` | Secret-management UI for authorized operators.
| Portainer | `https://portainer.tsw.local` | Deployment gateway after bootstrap.
| Nexus | `https://nexus.tsw.local` | Repository service and Docker proxy behavior.
| Jenkins | `https://jenkins.tsw.local` | CI service.
| Pulsar | `https://pulsar.tsw.local` | Pulsar Manager UI; use the catalog or effective override. The Infisical item is usable only after synchronization.
| Pulsar Admin API | `https://pulsar-api.tsw.local/admin/v2/clusters` | Requires the effective bearer token; browser reachability is not an authenticated API check.
| SonarQube | `https://sonarqube.tsw.local` | Static analysis service.
| Swagger/NGINX | `https://swagger.tsw.local` | API documentation surface.
| Traefik | ports `80` and `443` | Ingress owner for the service-access setup profile.
|===

Direct localhost ports such as `10000`, `10001`, `11080`, `12000`, `13081`,
`14080`, `14081`, `16081`, and `17080` are diagnostic or compatibility access.
They are not the preferred Service Access links. Localhost reachability depends
on the selected provider, LXC profile proxy state, WSL forwarding, and verified
stack deployment. Treat route defaults as operator targets, not proof that a
service is healthy.

[[infisical-credentials]]
== Get Infisical Credentials

Use the service-specific identifiers and password convention in the
link:{user-reference-prefix}arc42/08_configuration/internal-test-credential-catalog.md[credential catalog].
Portainer uses `admin`; Infisical uses its configured email address. The
catalog documents the SonarQube exception and component-specific derivations.
Do not assume every service uses the same username, or use password values
copied from chat history or logs.

Infisical has two distinct credential concerns:

* bootstrap login credentials for the Infisical UI;
* service credential entries synchronized into or referenced from Infisical.

The bootstrap login email and initial admin password are resolved during
installation from the deterministic catalog unless explicitly overridden in
the process environment or protected local source. The canonical internal-test
login identifier is `admin@tiny-swarm-world.local`; the catalog documents the
disposable password convention. The installer prints the URL and identifier,
but intentionally does not print password values.

For an explicit override, use the protected file selected by
`TSW_INSTALL_ENV_FILE` or the applicable configured source. A default install
does not create a file for you. Do not assume a key's presence alone proves
that its value is valid or in use.

For the standard internal-test path, use the catalog's documented disposable
login convention. For an explicit override, open the ignored local file in a
private terminal or editor to read the bootstrap email and password, then use
those values to sign in to Infisical at the configured Infisical route. The
default external URL is:

[source,text]
----
https://infisical.tsw.local
----

The direct `http://localhost:17080` URL remains a diagnostic compatibility
target when provider forwarding exposes it.

The installer uses the resolved catalog values and optional operator overrides
for Infisical bootstrap. It does not write a separate Infisical credential or
recovery file.

After signing in, use the Infisical UI to reveal or copy service secret values.
The Service Access dashboard intentionally shows only users and Infisical item
references; it does not display password values. If Infisical item
synchronization has not been enabled or completed, use the catalog for defaults
or your protected source for overrides. No generated local credential file is
implied; dashboard references are only navigation hints.

If service items are missing, check whether synchronization was enabled and
completed. See link:{user-guide-prefix}installation.adoc#optional-infisical-seeding[optional item
seeding] for a deliberate fresh run; do not reset an existing environment just
to populate missing items.

[[reset-or-destroy]]
== Reset Or Destroy A Disposable Environment

Reset and destroy require exact confirmation and live consent. Preserve needed
data first; these commands remove managed state and are not routine repairs.
Keep the installed backend, service profile and effective configuration.

[source,bash]
----
tiny-swarm-world --service-profile service-access platform reset --confirm RESET_TINY_SWARM_PLATFORM --live
tiny-swarm-world --service-profile service-access platform destroy --confirm DESTROY_TINY_SWARM_PLATFORM --live
----

These are alternatives, not consecutive steps. If ownership or guarded provider
settings block removal, follow
link:{user-guide-prefix}troubleshooting.adoc#_refused_workflow_confirmation_missing[the reset diagnosis]
before retrying. Do not delete unrelated Incus resources.

and run the full gate before handing off changes:

Available subcommands:

[source,bash]

== Main Python Entrypoint

After installing the repository in editable mode, the main workflow entry point
is:

[source,bash]
----
tiny-swarm-world
----

For source-checkout diagnostics before installation, the equivalent module
fallback remains `PYTHONPATH=src python3 -m tiny_swarm_world`.

[source,bash]
----

== Detect The Host Platform

Detect the host before preflight or setup:

[source,bash]
----
tiny-swarm-world host detect
----

For automation, request one deterministic JSON document:

[source,bash]
----
tiny-swarm-world --json host detect
----

The read-only result identifies `native_linux`, `wsl2`,
`wsl1_unsupported`, an unsupported/ambiguous host, or an explicitly
unverifiable sandbox. It reports the distribution, kernel release, Windows
interop availability, supported setup path, and remediation. WSL2 is a
dedicated supported platform; it is not reported as native Linux. A confirmed
WSL2 host can report Windows interop as unavailable without changing its host
type. WSL1 and ambiguous signals exit with status `1` after printing the
structured result and remediation.

The JSON result sets `live_readiness_verified` to `false`. Its
`allows_live_setup` field represents only the host-classification gate; it does
not bypass or predict the later filesystem, resource, provider, network,
deployment, or service-readiness gates. Human output states the same limitation
explicitly. Windows interop is reported as not applicable on native Linux.

`host detect` does not execute Incus, Docker, Windows, or network commands and
does not prove resource, filesystem, network, provider, deployment, or service
readiness. Those checks remain separate preflight/verify stages.

The dedicated host commands keep those stages visible:

[source,bash]
----
tiny-swarm-world host detect
tiny-swarm-world host preflight
tiny-swarm-world --live --approve-live host prepare
tiny-swarm-world --json host verify
----

`host preflight` runs the static host, filesystem and resource checks.
`host prepare` is the explicit, bounded host-preparation mutation boundary. On
WSL2 it verifies or reconciles the registered Windows bridge through the
dedicated infrastructure adapter; it does not perform platform deployment.
When the repository is on a Windows-mounted WSL filesystem, add
`--allow-wsl-windows-filesystem` and retain the emitted override evidence.
`host verify` collects bounded, read-only process and Docker diagnostics; it
does not repair networking, change Incus limits, or modify deployments.

== Check The Project Filesystem

Static preflight evaluates the repository filesystem immediately after the
typed host result without live-infrastructure consent:

[source,bash]
----
tiny-swarm-world --preflight
----

On WSL2, `HOST-FILESYSTEM` passes for the distribution's Linux filesystem and
blocks Windows-mounted checkouts such as `/mnt/c`, `/mnt/d`, or `/mnt/e` by
default. The detector resolves the project path and uses mount facts rather
than a fixed path prefix. Unknown or contradictory mount information also
blocks. The safe result includes no project path and recommends a checkout
below `/home/<user>/projects/Tiny-Swarm-World`.

For an intentional Windows-mounted checkout, place the global override before
the workflow command:

[source,bash]
----
tiny-swarm-world --allow-wsl-windows-filesystem --preflight
tiny-swarm-world --allow-wsl-windows-filesystem setup run --live
----

Static preflight shows the requested decision but writes no state. An accepted
live preflight or installer records the applied override in the protected
schema-v1 document below
`${XDG_STATE_HOME:-$HOME/.local/state}/tiny-swarm-world/installation/`.
Failure to verify the evidence target as Linux-native or WSL Linux, write it atomically, or
enforce owner-only permissions blocks before later setup actions. The override
does not bypass host, resource, provider, network, deployment, or service
readiness gates.

Non-mutating workflow checks can be selected explicitly:

[source,bash]
----
tiny-swarm-world platform verify
----

`platform verify` is non-mutating. It checks post-install preflight state,
managed LXC nodes, Docker Engine readiness, Swarm membership, profile-level
proxy devices, and Portainer endpoint reachability, reporting target,
expected state, observed state, and next action in verification evidence.

The safe setup probe is `setup run` without `--live`. It refuses before setup
services are constructed:

[source,bash]
----
tiny-swarm-world setup run
----

The canonical live operator command requires live-infrastructure consent before
services are constructed and uses `lxc_native` by default:

[source,bash]
----
tiny-swarm-world setup run --live
----

The setup sequence includes `platform expose`, which configures the
LXC-native manager gateway for published Swarm service ports after platform
init/reconcile and before deployment bootstrap.
Before any Incus or platform phase, `setup run` executes the explicit `host
prepare` and read-only `host verify` phases. On WSL2 these phases reconcile and
verify the Windows bridge; on native Linux they select the no-op native host
adapter.

Backend selection first honors an explicit `--lxc-backend incus` override,
then `backend_selection.preferred_backend` in
`infra/config/node-providers/provider_config.yaml`. Select the managed LXC
backend explicitly when the configured default should be made visible:

[source,bash]
----
tiny-swarm-world --lxc-backend incus setup run --live
----

The command prompts for a short confirmation:

[source,text]
----
Live setup can change local infrastructure. Continue? [y/N]:
----

Answer `y` only when changing local infrastructure is intentional. Without
`--live` and the short confirmation, the entry point reports
`REFUSED_LIVE_CONSENT_MISSING` before application services are constructed.

For destructive platform commands and their exact confirmation phrases, use
<<reset-or-destroy>>.

Reset and destroy are explicit confirmation contracts. Their destructive
execution is limited to configured managed LXC-native nodes whose Tiny Swarm
World ownership evidence is verified before mutation. Already absent managed
nodes count as successful evidence. Missing, mismatched, or unmanaged
ownership evidence blocks before deletion.

Artifact and deployment workflow command names are reserved by the CLI contract
and dispatch to guarded workflow contracts on the default `lxc_native` path.
They require live consent for mutating phases and report blocked or failed
phase evidence when live Nexus, registry, Portainer, Swarm, external-input, or
observed-state prerequisites are unavailable.

Optional live smoke validation is a separate operator action, not part of
`python3 tools/quality_gate.py quality`. Run `setup run --live` only on a
disposable or recoverable local environment and only when Incus/LXC or
provider state, Docker Swarm, networking, Portainer,
Nexus, Jenkins, Apache Pulsar, SonarQube, Swagger/NGINX, image, and stack changes
are intentional.

== Verification Scope

The workflow safety behavior is verified through unit tests, architecture
checks, import-linter contracts, type checks, and static command catalog
validation. The default quality gate does not run live Incus, LXC
container lifecycle, Docker Swarm, compose, netplan, socat,
Portainer, Nexus, Jenkins, Apache Pulsar, SonarQube, or Swagger/NGINX commands.

== Service Preparation

The workflow-level CLI is the supported setup surface. Portainer, Nexus, image
publication, stack deployment, and final verification belong to setup
boundaries. On the default `lxc_native` path they run only through guarded
artifact, deployment, external-input, and observed-state contracts and report
blocked or failed phase evidence when live prerequisites are unavailable:

[source,bash]
----
tiny-swarm-world setup run --live
----

Former direct service preparation helpers have been
retired and are not development quality-gate checks.

The workflow-level CLI is the supported operator entry point. Former direct

== Nexus Bootstrap

Nexus bootstrap is owned by the workflow-level setup command. Configuration can
be supplied with environment variables where supported by the Python adapters:

Important variables:

* `TSW_PORTAINER_URL`
* `TSW_PORTAINER_USERNAME`
* `TSW_PORTAINER_ADMIN_PASSWORD`
* `TSW_PORTAINER_ENDPOINT`
* `TSW_NEXUS_STACK_NAME`
* `TSW_NEXUS_URL`
* `TSW_NEXUS_ADMIN_USERNAME`
* `TSW_NEXUS_ADMIN_PASSWORD`
* `TSW_NEXUS_INITIAL_PASSWORD_PATH`
* `TSW_NEXUS_MAX_ATTEMPTS`
* `TSW_NEXUS_WAIT_SECONDS`

The current validated setup contract is documented in
`documentation/arc42/08_configuration/operator-configuration-contract.md`; `.env.example`
contains placeholders for every contract key. Preflight reports only key names,
scopes, value kinds and source classification, not secret values.

The standard internal-test installer resolves the central credential catalog.
Supply explicit values only when an override is intended. The direct CLI must
receive its required effective inputs through the operator contract; do not
assume the wrapper's resolution was applied to a separate process.

The managed Nexus stack provides a Docker Hub proxy repository. Its presence
does not establish that an image pull used that proxy: inspect the selected
image reference and managed-node registry configuration. Do not rely on a Nexus
stack that has not yet started as a prerequisite cache for fresh installation. The default proxy endpoint
inside the Swarm manager is `127.0.0.1:5001`, while the hosted local registry
for project-built images remains `127.0.0.1:5000`.

The former standalone Nexus cache helper was removed because it bypassed the
Python consent boundary, enabled anonymous access, rewrote the host Docker
daemon configuration, and restarted Docker. Use the managed Nexus proxy or an
operator-managed external cache instead.

When managed LXC nodes should use an operator-managed external cache during
installation, provide a Nexus address that is reachable from inside the LXC
nodes. Do not use `127.0.0.1`, because that would point at the node itself:

[source,bash]
----
export TSW_LXC_DOCKER_REGISTRY_MIRROR='http://<lxc-reachable-host-ip>:5001'
PYTHONPATH=src python3 -m tiny_swarm_world setup run --live
----

The LXC Docker installation step writes this value into each node's
`/etc/docker/daemon.json` as both `registry-mirrors` and
`insecure-registries`. Localhost values such as `http://127.0.0.1:5001` are
rejected for LXC nodes because they would point at the node itself, not at the
WSL-hosted Nexus cache.

Artifact source readiness supports the explicit modes `direct-internet`,
`nexus`, `fallback`, and `offline` through `TSW_ARTIFACT_SOURCE_MODE`. The
default is `direct-internet`; `fallback` probes the configured Nexus source and
then direct sources. `offline` is not an unconditional bypass: it requires a
checksum-verified manifest:

[source,bash]
----
export TSW_ARTIFACT_SOURCE_MODE=offline
export TSW_OFFLINE_ARTIFACT_MANIFEST=/home/<user>/artifact-cache/offline.json
----

The manifest must contain `contract_version: 1` and a non-empty `artifacts`
array. Each artifact has an identifier, a local `path`, and a lowercase SHA-256
`sha256` value. Preflight blocks when the manifest is missing, malformed, or a
cache checksum does not match; this keeps offline installation explicit and
reproducible.

== Stack Deployment

Stack deployment is owned by the workflow-level setup boundary. On the default
`lxc_native` path it runs only through guarded stack, external-input, and
observed-state contracts, and live success still requires explicit deployment
and readiness evidence. Direct Portainer upload scripts have been retired so
compose assets cannot bypass the CLI consent gate.

== Service Access Dashboard

The full guided setup selects the service-access stack profile by default. It
provides the intended management landing page contract for service links and
Infisical credential references after a verified provider-specific live
deployment. Operators who intentionally want only the older base service set
can pass `--service-profile default` to setup, deployment, or preflight
commands.

Implemented repository assets:

* `infra/config/compose/service-access/docker-compose.yml` defines the
  service-access dashboard and service-access NGINX services.
* `infra/config/compose/service-access/dashboard/**` contains the committed
  dashboard image asset rendered from the effective service-access model.
* `infra/config/compose/service-access/nginx/**` contains the image-packaged NGINX
  route configuration.

During LXC stack deployment, the dashboard HTML is rendered again from the
effective service-access model and synchronized to
`$\{TSW_REMOTE_STACK_ROOT}/service-access/dashboard/index.html` before the
service-access stack consumes its compose config. The committed dashboard file
is not the hidden deployment source of truth for that remote Swarm config
file.

When the default full profile is deployed by an operator workflow, the
dashboard route is available through the direct local compatibility port
`10000`. Traefik owns the public local ingress ports `80` and `443`, and the
service-access NGINX compose service also publishes `8086` as the local
Infisical compatibility route.
The dashboard is a generated management table with `Service`, `URL`, `User`
and `Password` columns. It links to the preferred Traefik-routed service
access URLs from the effective model, such as Jenkins, Nexus, Portainer,
Pulsar Manager, Pulsar Admin API, SonarQube, Swagger, Infisical and Service
Access.
It does not show password values.

For service routes and login steps, use <<open-the-services>> and
<<infisical-credentials>>. Dashboard item references do not prove that
synchronization or authentication has succeeded.

Prometheus, Grafana, app, and API links are configuration-dependent. An
optional link is rendered only when its service is enabled; disabled services
remain documented in the effective model as `service_not_enabled`. Preferred
links use routed HTTPS URLs and do not use diagnostic ports `10080` or `10443`.

== Effective Access Model Evidence

The deployment pre-apply step writes
`.tiny-swarm-world/evidence/solid-typed-evidence/routing/effective-access-model.json`
from the same model used for Traefik labels, dashboard links, and health
targets. The file is atomically replaced and contains no credential values:
only credential labels and Infisical item references are permitted. A failed
write blocks stack apply. `result: generated` means that the configured model
was serialized; it is not live reachability evidence.

== Routed Browser Evidence

The browser suite derives its expected routes from current
`service_access_links`. Each expected route is recorded as `passed`, `failed`,
`skipped`, or `missing`; missing evidence makes the suite fail. Disabled and
non-profile routes are not expected. Live Selenium remains opt-in, and absent
consent, Selenium, or approved credentials is retained as explicit redacted
skip evidence rather than blocking static quality gates.

The direct dashboard route is `http://localhost:10000`. Localhost reachability
still requires provider-specific exposure and verified deployment evidence.
